# AutoZap ERP

Реализация по [ТЗ](TZ_AutoZap.md): Django 5 + DRF + PostgreSQL (бэкенд) и React + TypeScript + Tailwind (фронтенд).

MVP по ТЗ реализован полностью: склад (приход/перемещение/инвентаризация/списание), продажа с торгом и тремя способами оплаты, дефицит-индикатор, подтверждение перед продажей, кассовые смены, товары/бренды/категории в интерфейсе (создание «на лету» из прихода), отчёты с графиками и экспортом в Excel. См. «Что дальше» внизу — там только пункты 2-го/3-го этапа (печать чеков, сканер штрихкода, PWA и т.п.), не блокирующие использование.

## Структура

```
project/
├── backend/     Django + DRF API
├── frontend/    React + Vite + Tailwind SPA
├── docker-compose.yml
└── .env.example
```

## Быстрый старт (локально, без Docker)

### Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo      # создаёт склады, демо-пользователей и 5 демо-товаров
python manage.py runserver 0.0.0.0:8000
```

По умолчанию используется SQLite (файл `backend/db.sqlite3`) — этого достаточно для разработки и первого знакомства с системой. Для продакшена используйте PostgreSQL (см. `docker-compose.yml` и `.env.example`, переменная `DATABASE_URL`).

Демо-пользователи (создаются командой `seed_demo`):

| Логин | Пароль | Роль |
|---|---|---|
| `owner` | `owner12345` | Владелец |
| `stock` | `stock12345` | Менеджер склада |
| `seller` | `seller12345` | Продавец |

**⚠️ Обязательно смените эти пароли (или удалите демо-пользователей и создайте новых через `/admin/`) перед реальной эксплуатацией.**

Админка Django: http://localhost:8000/admin/
Документация API (Swagger): http://localhost:8000/api/docs/

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173 — в dev-режиме Vite проксирует все запросы `/api/*` на `http://127.0.0.1:8000` (см. `vite.config.ts`), поэтому backend должен быть запущен параллельно.

## Запуск в продакшене (Docker Compose)

```bash
cp .env.example .env
# отредактируйте .env: SECRET_KEY, ALLOWED_HOSTS, пароль базы данных

docker compose up -d --build
docker compose exec backend python manage.py createsuperuser
# либо
docker compose exec backend python manage.py seed_demo
```

Приложение будет доступно на порту 80 (фронтенд + прокси на API). Добавьте Nginx/Caddy с Let's Encrypt перед этим стеком для HTTPS на реальном домене (см. ТЗ §12.1), либо поставьте `docker-compose` за уже существующий reverse proxy.

## Управляющие команды (важно для целостности данных)

Согласно ТЗ §5.4/§10.1 остатки (`Stock`) — это кэш, источник истины — журнал движений (`StockMovement`). Для проверки и восстановления целостности:

```bash
python manage.py verify_stock   # сверяет Stock с журналом движений, печатает расхождения
python manage.py recalc_stock   # пересчитывает Stock из журнала (использовать при расхождениях)
```

Рекомендуется добавить `verify_stock` в ежедневный cron/health-check.

## Деплой демо на Vercel

На Vercel проект разворачивается как **два отдельных проекта из одного репозитория**:
`backend` (Django) и `frontend` (Vite SPA). Так работает штатное zero-config
определение фреймворка: Vercel находит `manage.py` и сам поднимает Django как
Vercel Function, а Vite-проект собирает как статику на CDN.

> **Не пытайтесь уместить оба в один проект через ключ `services` в `vercel.json`.**
> Эта возможность включается отдельными правами (в документации помечена
> «Permissions Required: Services») и на плане Hobby недоступна — отсюда были
> непонятные ошибки сборки и роутинга.

### Шаг 1. Бэкенд

1. Vercel → **Add New… → Project** → импортируйте репозиторий.
2. **Project Name:** `autoerp-api`.
3. **Root Directory:** нажмите *Edit* и выберите **`backend`** — это самый
   важный пункт, без него Vercel не найдёт Django.
4. Framework Preset менять не нужно — определится автоматически.
5. Разверните **Environment Variables** и добавьте:

   | Переменная | Значение |
   |---|---|
   | `SECRET_KEY` | любая длинная случайная строка |
   | `DEBUG` | `False` |

6. **Deploy**. Первая сборка **намеренно остановится** с сообщением
   «Сборка остановлена: не подключена база данных». Так и задумано: на Vercel
   файловая система доступна только на чтение, поэтому без внешней базы демо
   было бы нерабочим (открывалось бы, но не сохраняло ни одной продажи).
7. Вкладка **Storage → Create Database → Postgres (Neon) → Connect to Project**.
   Vercel сам добавит `DATABASE_URL`.
8. Вкладка **Deployments** → у последнего деплоя меню `⋯` → **Redeploy**.
   Теперь сборка выполнит миграции и загрузит демо-данные.
9. Проверьте: `https://<адрес-бэкенда>/api/health/` должен вернуть
   `{"status": "ok"}`, а `https://<адрес-бэкенда>/admin/` — открыть админку.

Скопируйте адрес бэкенда (вида `https://autoerp-api-xxxx.vercel.app`) — он нужен
на следующем шаге.

### Шаг 2. Фронтенд

1. **Add New… → Project** → тот же репозиторий.
2. **Project Name:** `autoerp`.
3. **Root Directory:** **`frontend`**.
4. Framework Preset определится как **Vite**.
5. **Environment Variables:**

   | Переменная | Значение |
   |---|---|
   | `VITE_API_URL` | адрес бэкенда из шага 1, **без `/` на конце** |

6. **Deploy**. Готово — открывайте адрес фронтенда и заходите под демо-логином.

> Vite подставляет `VITE_API_URL` в бандл **на этапе сборки**, а не в браузере.
> Если добавите или измените переменную позже — обязательно сделайте **Redeploy**,
> иначе фронтенд продолжит стучаться на старый адрес.

Права CORS настраивать не нужно: бэкенд уже разрешает запросы с любого поддомена
`*.vercel.app`, включая preview-деплои (`settings.py`,
`CORS_ALLOWED_ORIGIN_REGEXES`). На реальном домене замените это на конкретный
адрес через переменную `CORS_ALLOWED_ORIGINS`.

### Чего не делать

- **Не копируйте переменные из `.env.example` в Vercel.** Там нужны только
  `SECRET_KEY` и `DEBUG`. `ALLOWED_HOSTS` из примера содержит плейсхолдер
  `erp.your-domain.kz`, который не совпадает с реальным `*.vercel.app`, и Django
  начинает отвечать пустым «400 Bad Request» вообще на все запросы — включая
  логин и `/api/health/`. `CORS_ALLOWED_ORIGINS` и `POSTGRES_*` оттуда тоже не
  нужны: первый уже настроен в коде, второй относится к docker-compose.
- Не задавайте Build Command и Output Directory вручную — они уже описаны в
  `backend/vercel.json` и определяются автоматически для фронтенда.

### Как это устроено внутри

- `backend/vercel.json` — задаёт Build Command `python vercel_build.py`.
- `backend/vercel_build.py` — выполняет `migrate` и `seed_demo` **на этапе
  сборки**. Это единственный момент, когда на Vercel вообще можно выполнить
  миграции: во время запроса файловая система только для чтения, а «зайти на
  сервер и выполнить команду» негде. Раньше миграции запускались при холодном
  старте прямо из `wsgi.py` — на read-only системе они молча падали в лог, и
  приложение отвечало 500 на каждый запрос.
- `collectstatic` вызывать не нужно: Vercel запускает его сам и раздаёт статику
  с CDN (в том числе стили админки).
- `frontend/vercel.json` — SPA-fallback, чтобы прямые ссылки и обновление
  страницы (`/sale`, `/products`, …) не отдавали 404.
- Демо-данные создаются при каждой сборке идемпотентно. Чтобы этого не
  происходило, задайте `AUTOZAP_SEED_DEMO=0`.

Демо-логины — те же, что при локальном `seed_demo` (таблица выше).

**Это конфигурация для демонстрации, не для боевой эксплуатации.** На реальном
сервере держите `AUTOZAP_SEED_DEMO=0`, поменяйте демо-пароли и сузьте
`ALLOWED_HOSTS`/`CORS_ALLOWED_ORIGINS` до своего домена.

## Тесты

```bash
cd backend
source venv/bin/activate
python manage.py test apps
```

36 тестов покрывают самую критичную логику: атомарность продажи, идемпотентность, лимит скидки по роли, продажу ниже себестоимости, защиту от продажи сверх остатка (и откат при ошибке), возврат товара, проведение прихода (включая пересчёт средневзвешенной себестоимости), перемещения (включая откат при нехватке товара), инвентаризацию, списание, скрытие закупочных цен от роли «продавец», автогенерацию кода товара, экспорт отчётов в Excel и команды `verify_stock`/`recalc_stock`.

## Что уже реализовано и проверено

- Модели: пользователи с ролями (владелец/склад/продавец), товары с толерантным поиском по OEM-коду, склады, остатки, неизменяемый журнал движений, приход, перемещение (с автоподбором дефицита), инвентаризация, списание.
- **Продажа**: атомарная транзакция, блокировка строк остатка (`SELECT FOR UPDATE`), идемпотентность по ключу, редактируемая цена (торг) с лимитом скидки по роли и флагом `needs_approval`, смешанная оплата (наличные/Kaspi QR/карта), проверка на продажу сверх остатка (`409 insufficient_stock`).
- Возврат товара (API + пересчёт статуса чека).
- Кассовые смены (открытие/закрытие со сверкой наличных) — в интерфейсе и в API.
- Отчёты: дашборд (сегодня/7д/30д, графики), дневной отчёт (Z-отчёт), отчёт по скидкам, остаткам, неликвидам; экспорт дневного отчёта и остатков в Excel.
- Разграничение прав: продавец не видит закупочные цены и себестоимость ни в API, ни в интерфейсе, ни в Excel-выгрузке.
- Фронтенд: авторизация (JWT + автообновление токена), дашборд с графиками, экран продажи (поиск → корзина → торг → оплата → модальное подтверждение) с индикатором смены, товары (создание/редактирование/архивация, быстрое добавление бренда/категории), остатки с цветовой индикацией дефицита, журнал продаж с карточкой чека и оформлением возврата, разделы склада — приход (включая создание нового товара «на лету»), перемещение (с кнопкой автоподбора дефицита), инвентаризация, списание — каждый с созданием документа и модальным подтверждением перед проведением. Адаптивная вёрстка (мобильное меню).
- Управляющие команды `seed_demo`, `verify_stock`, `recalc_stock`.
- 36 автотестов на самую критичную бизнес-логику (см. раздел «Тесты» выше).
