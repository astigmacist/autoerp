# AutoZap ERP

Реализация по [ТЗ](TZ_AutoZap.md): Django 5 + DRF + PostgreSQL (бэкенд) и React + TypeScript + Tailwind (фронтенд).

MVP по ТЗ реализован полностью: склад (приход/перемещение/инвентаризация/списание), продажа с торгом и тремя способами оплаты, дефицит-индикатор, подтверждение перед продажей, кассовые смены, товары/бренды/категории в интерфейсе (создание «на лету» из прихода), отчёты с графиками и экспортом в Excel. См. «Что дальше» внизу — там только пункты 2-го/3-го этапа (печать чеков, сканер штрихкода, PWA и т.п.), не блокирующие использование.

## Структура

```
project/
├── backend/     Django + DRF API (+ spa/ — собранный фронтенд для деплоя)
├── frontend/    React + Vite + Tailwind SPA (исходники)
├── docker-compose.yml
└── .env.example
```

## Быстрый старт (локально, без Docker)

### Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
echo "DEBUG=True" > .env        # только для разработки: подробные ошибки и статика на лету
python manage.py migrate
python manage.py seed_demo      # создаёт склады, демо-пользователей и 5 демо-товаров
python manage.py runserver 0.0.0.0:8000
```

`DEBUG` по умолчанию выключен, чтобы случайно запущенный на сервере экземпляр
не показывал посетителям трассировки. Для локальной работы его включают одной
строкой в `backend/.env`, как выше.

По умолчанию используется SQLite (файл `backend/db.sqlite3`) — этого достаточно для разработки и первого знакомства с системой. Для продакшена используйте PostgreSQL (см. `docker-compose.yml` и `.env.example`, переменная `DATABASE_URL`).

Демо-пользователи (создаются командой `seed_demo`):

| Логин | Пароль | Роль |
|---|---|---|
| `owner` | `owner12345` | Владелец |
| `stock` | `stock12345` | Менеджер склада |
| `seller` | `seller12345` | Продавец |

**⚠️ Обязательно смените эти пароли (или удалите демо-пользователей и создайте новых через `/admin/`) перед реальной эксплуатацией.**

Админка Django: http://localhost:8000/admin/
Документация API (Swagger): http://localhost:8000/api/docs/

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173 — в dev-режиме Vite проксирует все запросы `/api/*` на `http://127.0.0.1:8000` (см. `vite.config.ts`), поэтому backend должен быть запущен параллельно.

## Запуск на своём сервере (Docker Compose)

```bash
cp .env.example .env
```

Отредактируйте `.env` — это обязательный шаг, без него приложение не запустится:

| Переменная | Что поставить |
|---|---|
| `SECRET_KEY` | случайная строка: `python -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `DEBUG` | `False` |
| `ALLOWED_HOSTS` | ваш домен, например `erp.avtozapchasti.kz` |
| `CORS_ALLOWED_ORIGINS` | `https://` + тот же домен |
| `POSTGRES_PASSWORD` | свой пароль базы |
| `USE_HTTPS` | `False` на первом запуске, `True` после того, как заработает сертификат |

```bash
docker compose up -d --build
docker compose exec backend python manage.py createsuperuser
```

Приложение поднимется на порту 80. Миграции и сборка статики выполняются
автоматически при старте контейнера (`backend/entrypoint.sh`), база —
PostgreSQL 16 в отдельном контейнере с постоянным томом.

Дальше поставьте перед стеком Nginx или Caddy с сертификатом Let's Encrypt,
после чего переключите `USE_HTTPS=True` и перезапустите:
`docker compose up -d`.

### Чек-лист перед первым рабочим днём

1. **Свой `SECRET_KEY`** — приложение не стартует со значением по умолчанию,
   но проверьте, что подставили именно свой.
2. **`DEBUG=False`** и `ALLOWED_HOSTS` со своим доменом.
3. **Демо-пользователей нет.** Команду `seed_demo` на боевом сервере запускать
   не нужно — она создаёт пользователей с общеизвестными паролями
   (`owner/owner12345`). Заведите реальных через `createsuperuser` и `/admin/`.
   Если демо-данные всё-таки попали в базу, удалите этих пользователей.
4. **HTTPS** включён, `USE_HTTPS=True`.
5. **Резервные копии настроены** (см. ниже) — это единственное, что нельзя
   восстановить, если сервер потеряется.
6. Проверьте `/api/health/` — должен отвечать `{"status": "ok"}`.

### Резервные копии

Для магазина это самое важное после самих данных. Снять копию:

```bash
docker compose exec -T db pg_dump -U autozap autozap | gzip > autozap-$(date +%F).sql.gz
```

Восстановить:

```bash
gunzip -c autozap-2026-09-05.sql.gz | docker compose exec -T db psql -U autozap -d autozap
```

Ежедневная копия в 3 ночи с хранением 14 дней (`crontab -e` на сервере):

```
0 3 * * * cd /path/to/project && docker compose exec -T db pg_dump -U autozap autozap | gzip > /var/backups/autozap-$(date +\%F).sql.gz && find /var/backups -name 'autozap-*.sql.gz' -mtime +14 -delete
```

Копии стоит регулярно уносить с сервера (в облако или на другой диск): копия,
лежащая рядом с базой, не спасёт при потере сервера. И раз в пару месяцев
проверяйте, что копия **разворачивается** — непроверенная копия не считается.

### Целостность данных

Согласно ТЗ §5.4/§10.1 остатки (`Stock`) — это кэш, источник истины — журнал движений (`StockMovement`). Для проверки и восстановления целостности:

```bash
python manage.py verify_stock   # сверяет Stock с журналом движений, печатает расхождения
python manage.py recalc_stock   # пересчитывает Stock из журнала (использовать при расхождениях)
```

Рекомендуется добавить `verify_stock` в ежедневный cron/health-check.

## Деплой на Vercel

Проект разворачивается **одним проектом и без единой настройки**:

1. Vercel → **Add New… → Project** → импортируйте репозиторий.
2. **Root Directory** → *Edit* → выберите **`backend`**.
3. **Deploy**.

Всё. Переменные окружения задавать не нужно, базу данных подключать не нужно.
После сборки открывайте адрес проекта и заходите под демо-логином из таблицы
выше. Админка — по адресу `/admin/`, проверка живости — `/api/health/`.

### Как это устроено

Django обслуживает и API, и сам интерфейс, поэтому проект на Vercel нужен один:

- Собранный фронтенд лежит в репозитории (`backend/spa/`, собирается командой
  `npm run build:demo`). Vercel сам выполняет `collectstatic`, поэтому js и css
  раздаются с CDN, а не через Python.
- Всё, что не `/api/`, не `/admin/` и не `/static/`, отдаёт `index.html` —
  дальше маршрут разбирает React Router. Поэтому прямые ссылки и обновление
  страницы (`/sale`, `/products`, …) работают.
- Django на Vercel определяется автоматически: платформа находит `manage.py` и
  берёт точку входа из `WSGI_APPLICATION`. Ключ `services` в `vercel.json`
  **не используется** — эта возможность требует отдельных прав («Permissions
  Required: Services» в документации) и на плане Hobby недоступна; попытки
  собрать проект через неё и давали непонятные ошибки.
- Миграции выполняются на этапе сборки (`backend/vercel_build.py`) — на
  serverless-хостинге это единственный момент, когда их вообще можно выполнить.

### Данные: демо-режим и постоянное хранение

Без подключённой базы приложение работает на SQLite во временном каталоге —
единственном месте, куда serverless-функции разрешено писать. Данные в этом
режиме **живут до перезапуска экземпляра**: для показа демо этого достаточно
(каждый показ начинается с одинакового набора демо-данных), для постоянного
хранения — подключите базу:

**Storage → Create Database → Postgres (Neon) → Connect to Project**, затем
**Deployments → ⋯ → Redeploy**.

Приложение переключится само: код читает `DATABASE_URL` (и `POSTGRES_URL`),
менять ничего не нужно. Если база вдруг окажется недоступна, вместо пустой
500-й страницы покажется понятное сообщение с этой же инструкцией.

### Если меняли фронтенд

Пересоберите интерфейс и закоммитьте результат, иначе задеплоится старая версия:

```bash
cd frontend
npm run build:demo     # собирает в backend/spa/
```

### Чего не делать

**Не копируйте переменные из `.env.example` в Vercel.** Они предназначены для
`docker-compose`. `ALLOWED_HOSTS` из примера содержит плейсхолдер
`erp.your-domain.kz`, который не совпадает с реальным `*.vercel.app`, и Django
начинает отвечать пустым «400 Bad Request» вообще на все запросы — включая
логин и `/api/health/`. Именно это и произошло на прошлом стенде.

**Это конфигурация для демонстрации, не для боевой эксплуатации.** На реальном
сервере (VPS + docker-compose, см. выше) подключите Postgres, поставьте
`AUTOZAP_SEED_DEMO=0`, смените демо-пароли и сузьте `ALLOWED_HOSTS` до своего
домена.

## Тесты

```bash
cd backend
source venv/bin/activate

```

36 тестов покрывают самую критичную логику: атомарность продажи, идемпотентность, лимит скидки по роли, продажу ниже себестоимости, защиту от продажи сверх остатка (и откат при ошибке), возврат товара, проведение прихода (включая пересчёт средневзвешенной себестоимости), перемещения (включая откат при нехватке товара), инвентаризацию, списание, скрытие закупочных цен от роли «продавец», автогенерацию кода товара, экспорт отчётов в Excel и команды `verify_stock`/`recalc_stock`.

## Что уже реализовано и проверено

- Модели: пользователи с ролями (владелец/склад/продавец), товары с толерантным поиском по OEM-коду, склады, остатки, неизменяемый журнал движений, приход, перемещение (с автоподбором дефицита), инвентаризация, списание.
- **Продажа**: атомарная транзакция, блокировка строк остатка (`SELECT FOR UPDATE`), идемпотентность по ключу, редактируемая цена (торг) с лимитом скидки по роли и флагом `needs_approval`, смешанная оплата (наличные/Kaspi QR/карта), проверка на продажу сверх остатка (`409 insufficient_stock`).
- Возврат товара (API + пересчёт статуса чека).
- Кассовые смены (открытие/закрытие со сверкой наличных) — в интерфейсе и в API.
- Отчёты: дашборд (сегодня/7д/30д, графики), дневной отчёт (Z-отчёт), отчёт по скидкам, остаткам, неликвидам; экспорт дневного отчёта и остатков в Excel.
- Разграничение прав: продавец не видит закупочные цены и себестоимость ни в API, ни в интерфейсе, ни в Excel-выгрузке.
- Фронтенд: авторизация (JWT + автообновление токена), дашборд с графиками, экран продажи (поиск → корзина → торг → оплата → модальное подтверждение) с индикатором смены — в каждой строке видны цена по прайсу, цена продажи, размер скидки в тенге и процентах, кнопки быстрых скидок и возврат к прайсу; товары (создание/редактирование/архивация, быстрое добавление бренда/категории), остатки с цветовой индикацией дефицита, журнал продаж с карточкой чека и оформлением возврата, разделы склада — приход (включая создание нового товара «на лету»), перемещение (с кнопкой автоподбора дефицита), инвентаризация, списание — каждый с созданием документа и модальным подтверждением перед проведением. Интерфейс приспособлен к телефону: нижняя панель навигации, списки в виде карточек вместо широких таблиц, увеличенные области нажатия, итог и кнопка оформления всегда под рукой на экране кассы. Тема (светлая/тёмная) переключается вручную и запоминается; экран входа всегда светлый.
- Управляющие команды `seed_demo`, `verify_stock`, `recalc_stock`.
- 36 автотестов на самую критичную бизнес-логику (см. раздел «Тесты» выше).
